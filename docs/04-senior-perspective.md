# 04. シニア視点との照合

思想が個人の知見にとどまっていないかを、研究と実務の知見に照らして確認した結果。
出典の詳細は [references.md](references.md) を参照。

## 結論

思想は、シニアの読み方とほぼ一致している。足りない視点が3つあった。

## 一致している点

| 思想・やり方 | 対応する知見 |
|---|---|
| 抽象（全体）から入る | Googleのレビュー指針: 全体像をつかむ → 主要な部分を調べる → 残りを適切な順で見る |
| 何のための処理かを先に持つ | シニアは「どこにコードを足すか」ではなく「このシステムは何をしようとしているか」を問う |
| 上から順に全部は読まない | 先頭から順に全部読む方法は、コードでは破綻するという指摘 |
| 入出力の例（値の変化）を見せる | 『プログラマー脳』: 状態の表や依存グラフで作業記憶を補う |
| 理解せずにマージしない | Googleの指針: 人が書いたコードは全行に目を通し、何をしているかは理解する |
| 仮説 → 検証 | Brooks のトップダウンモデル |
| 情報を絞る | 作業記憶とレビュー成績の研究、混ざった変更の研究 |
| 関連する変更をまとめ、必要な順に出す | Baum らの読む順番の原則 |

## 足りない視点

### 1. 理解の前に「この変更は妥当か」を判断する
- Googleの指針は、そもそも行うべきでない変更なら、すぐに理由を添えて返すよう求めている。
- 大枠の方針が間違っていれば、実装の細部をレビューする意味はない。
- 示唆: 概要と図の段階で、詳細を読まずに差し戻しを判断できる作りにする。一番の時間短縮は、読まなくてよいPRを早く見分けること。

### 2. diffに写っていないものを見る
- レビューツールは変更箇所の前後数行しか見せない。広い文脈で見ることが役に立つ。
- データの旅は「書かれたコード」しか通らない。
- 示唆: 変更の影響を受ける既存コードや、書かれていない異常系を、別に示す必要がある。

### 3. ドメインの言葉を知らないと、きれいなコードでも読めない
- 短期記憶と作業記憶は、長期記憶（すでに知っていること）に依存する。
- 示唆: PRに出てくる新しいドメイン用語を、最初の抽象の段階で短く定義しておく。

## 採用しない知見

- **テストを先に読むべきか**: 推奨する記事と、逆効果とする記事があり、意見が割れている。思想には入れない。

## 未決

上の3つの視点を、思想に加えるか、設計原則の段階で扱うか。

## 参考: 調査で整理したマインドマップ

「PRを速く理解する」ための知見を6つの枝に整理した。

| 枝 | 分類 | 要点 |
|---|---|---|
| 理解の仕組み | 読み手の頭の中 | 仮説を立てて検証（トップダウン）／細部から積み上げ（ボトムアップ）／実際は状況で切り替える |
| 認知負荷 | 読み手の頭の中 | 作業記憶を超えると崩れる／無関係な変更の混在が負荷を上げる／離れた箇所を結びつける作業が重い |
| レビュアーが欲しい情報 | PRの渡し方 | 代替案、正しい理解、変更の理由／実行される文脈、本当に必要か／詳しい人は誰か、分割できるか |
| 読む順番 | PRの渡し方 | 関連する変更をまとめる／必要な情報は先に出す／並べ方のルールを読み手に示す |
| 量とペース | 量と環境 | 一度に200〜400行まで／1時間に300〜500行が目安／約60分を過ぎると効果が落ちる |
| AI時代の変化 | 量と環境 | 理解より先にコードが入る／負担が作者からレビュアーへ移る／量だけでなくコード自体が難解 |

ツールへの示唆は3つに集約される。

1. 最初の仮説を読み手に渡す
2. 関連する変更をまとめて、必要な順に出す
3. 頭の容量を空ける

量とペースの数字（SmartBear / Cisco の調査）についての注意: 調査主体はレビューツールのベンダー。測っているのは欠陥発見率で、理解の速さではない。AI普及前のデータ。
