# 01. 背景と課題

## 何が起きているか

- AIによって、コードを書く速度は上がった。
- その分、「このコードをリリースしてよいか」の責任を持つ人間の側に負担が寄っている。
- レビューでコードを読んでも理解できず、理解しようとすると時間がかかる。
- 実測: PRレビューからマージまでの時間が、1年前は約20時間、最近は約47時間。

この状態を「理解負債」と呼ぶ。理解が追いつく前に、動くコードがシステムに入っていく。

## 問題の所在

- 自分が出すPRは問題ない。設計が仕事の中心になっており、実装前に方針が固まっている。
- 問題は**他の人が出すPR**。何をしているコードなのか理解できない。
- これはAIの有無に関係なく以前からあった問題。ただし、AIによってコード量が単純に増え、レビュー時間が延びた。
- 理解していないコードはマージすべきではない。特にドメインコード。
  - したがって「読む量を減らす」「流し読みで済ませる」は解決にならない。
  - 解くべきは「**理解する速度をいかに上げるか**」。

## すでにやっていること（現在の読み方）

1. 読み始める前に、AIに説明させる。
2. アーキテクチャの説明とデータの流れで、最初に概要を把握する。
3. データの流れごとに、上から詳細なコードを読んでいく。

意識していること:

- AIの補足情報は、人間にとって情報量が多すぎる。脳がパンクする。
- 不要なインターフェースや型定義などは、情報量の圧迫につながる。いかに省くかが大事。
- **抽象と具体**を意識する。抽象で「今から何を理解するのか」を把握し、具体で実際のコードやデータを追う。

## 実務で作っているツール（現状）

現在、実務で次のようなツール（スキル）を作って使っている。pr-tabiji はこれをブラッシュアップしてOSSにするもの。

1. はじめに、どんな変更・追加があったかの概要を3行程度で示す。
2. アーキテクチャの説明と、データの流れをMermaidやフローチャートで示す。
3. エンドポイント → DTO → ドメイン → リポジトリの順に、上から何をするのかを説明する。
4. データフローの大まかな処理ごとに、次をセットでレビューできる。
   - 左: 日本語の類似コード（擬似コード）
   - 右: 実際のコード
   - 日本語側・コード側のどちらかをクリックすると、対応する箇所がフォーカスされる。
   - その際、上部に「こんなデータが入力されたら、こういう出力になる」という具体的な入出力の例が出る。

## 現状のツールの悩み

- 分かりやすいような、分かりにくいような状態。都度の部分最適を繰り返した結果、全体が微妙になってきた。
- 層ごと（エンドポイント、DTO、ドメイン、リポジトリ）と処理単位ごとの両方でコードを読むと、重複する可能性がある。
- 日本語の類似コードは、プログラムをそのまま言語化している（「〜の処理をする」）。役に立っているのかよく分からない。
- 自分のやり方が最善とは限らない。メンタルモデルから考え直したい。

## 遅くなる原因の仮説

PRレビューは「理解の枠組みをつくる」段階と「検証する」段階に分かれ、時間がかかるのは前者。

| 原因 | 内容 |
|---|---|
| 意図が分からない | なぜこの変更をしたのかが分からず、仮説が立てられない |
| 情報が多すぎる | 判断に関係ない型やつなぎ込みのコードが、頭の容量を圧迫する |
| 読む順番が悪い | diffはファイル順に並んでいるだけで、理解しやすい順ではない |
| 抽象と具体がつながらない | 構造は分かっても、実際にどう動くかが頭に浮かばない |

手助けの方向は「**仮説を先に渡す**」と「**頭の容量を空ける**」の2つに集約される。

## 計測についてのメモ

47時間の内訳（レビュー開始までの待ち時間／読んでいる時間／差し戻しの往復）は未分解。
どれが延びているかで効く対策が変わるため、分解できれば効果測定の基準になる。
