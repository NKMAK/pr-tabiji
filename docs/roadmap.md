詳細に入りすぎず、上位から順に決める。

| # | 段階 | 状態 |

## 提供形態についてのメモ（未決）

どの原因を解決したいかで、向いている形が変わる。

| 解決の仕方 | 向いている形 |
|---|---|
| 説明の仕方で解決する（意図、抽象と具体） | スキル |
| 見え方で解決する（ノイズを隠す、読む順に並べ替える、左右に並べてフォーカス） | diffの表示を変えるツール・アプリ |
| 作者側で解決する（意図を書かせる） | PRテンプレート、CI |

第一歩の案: AI CLI向けのスキルとして出し、PRを渡すと読み物をHTMLで出力する。使われ方を見てから専用のビューアに進む。

## OSSにするときの方針メモ

- 社内固有の部分（プロジェクト名、ドメイン用語、社内規約）を外し、どのコードベースにも当てはまる原則だけを残す。
- ルールより原則を書く。理由と例をセットにする（AIが状況に応じて判断しやすくなる）。
- 抽象と具体の往復を中心に据える。
- READMEに使用前後の比較を載せる（同じPRで、普通に説明させた場合と比べる）。
- スキルとして出すなら SKILL.md 形式に合わせる。

## 未決事項

1. シニア視点の3点（妥当性の早期判断／diffに写らないもの／ドメイン用語）を、思想に加えるか、設計原則で扱うか（[04-senior-perspective.md](concept/04-senior-perspective.md)）
2. 値の変化を、実際に実行した結果に基づかせるか（正しさをどう担保するか。人が全部は見られないので、AI 用の検証環境を作って改善したい）
3. 入出力の例を「変わった項目だけ」に絞るか
4. 解説とコードの一致を検証する仕組みを入れるか
5. 提供形態の残り: コマンドの形（Claude Code のスキルか CLI か）、アーティファクトの制約（外部への通信不可、1ページ、共有は claude.ai 内）への対処
6. 対象とする言語・アーキテクチャの範囲（エンドポイント → DTO → ドメイン → リポジトリ以外の構成をどう扱うか）
7. 説明の言語（日本語以外への対応）
8. 効果の測り方（レビューからマージまでの時間の内訳をどう取るか）
