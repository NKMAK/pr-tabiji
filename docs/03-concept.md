# 03. コンセプト（路線図とデータの旅）

思想（[02-philosophy.md](02-philosophy.md)）を、読み物の構造に落としたもの。
要件定義としてはまだ叩き台で、詳細は設計原則・機能要件の段階で詰める。

## 3段のズーム

1. **地図**: 目的、挙動の変化、読み手が持つべき最初の仮説
2. **データの旅**: 具体的な入力を1つ決め、変更されたコードを通るたびに、値がどう変わるかを示す
3. **行の解説**: 知りたい箇所だけを開いて読む。型定義や定型コードは最初から折りたたんでおく

## 構造: 路線図と、データの旅

読む軸を「データの旅」1本に絞る。
層（エンドポイント、DTO、ドメイン、リポジトリ）は別に読むものではなく、**データが通過する駅**として扱う。
これにより、層ごとと処理ごとで同じコードを二重に読む問題が解消する。

### 1. 行き先（抽象）
- このPRで何がどう変わるかを3行程度で書く。
- 確かめるべき仮説を並べる。

### 2. 路線図（抽象と具体の橋渡し）
- アーキテクチャ図の上で、今回変わった駅を強調する。
- データの通り道を線で示す（Mermaidやフローチャート）。

### 3. 旅（具体）
例のデータを1つ持って、駅を順にたどる。各駅の中身は次の3つ。

- この駅で確かめる仮説を1行（例: 「在庫が足りない注文はここで弾かれるはず」）
- コードと、日本語の意味
- 値の変化（入る前と出た後）

どの駅も、出てくるのは1回だけ。

### 4. 別ルート
境界値やエラーのケースは、最初から読み直さない。分岐する駅からの差分だけを見せる。

### 5. 車庫
どの旅も通らない変更（型、設定、リネームなど）は、まとめて軽く確認する。
ここに重要そうなコードが残っていたら、「旅が足りない」というサインになる。

### この形で解決すること
- **重複が出ない**: コードは、データが最初に通過した駅で一度だけ登場する。
- **ちぐはぐにならない**: どのセクションも「仮説か証拠か」という同じ原則から生まれている。
- **レビュー完了の基準が明確になる**: すべての仮説が確認済みになった時点が、マージの判断ができる時点。確認できなかった仮説は、そのままレビューコメントになる。

## 例データの選び方

- 全部の行を読むのではなく、データが通る行を読む。通らない行は、今回の挙動に関係しない可能性が高い（車庫で確認する）。
- 例は戦略的に選ぶ。正常系、境界値、ルールで弾かれるケースなど、ドメインのルールを必ず通る例にする。
- 値は、可能なら実際に実行して確かめる。AIが説明する値の変化は間違うことがある。例をテストとして走らせ、表示する値を実行結果に基づかせれば、「説明が正しいのか」という不安がなくなる（差別化の候補。採否は未決）。

## 日本語の類似コード（左右に並べる表示）

### 残すもの
- 左に日本語、右に実際のコードを並べる。
- どちらかをクリックすると、対応する箇所がフォーカスされる。
- フォーカスした範囲に応じて、上部に入出力の例が出る。

### 変えるもの: 翻訳ではなく「意味」を書く

行ごとの翻訳は、仮説でも証拠でもない。同じ内容を同じ粒度で言い換えているだけで、コードが読める人には読む量が倍になる。
日本語側は、コードより**一段抽象度を上げて**書く。

```
if (stock.available < order.quantity) {
  throw new InsufficientStockError(order.id)
}
```

- 翻訳（現状）: 「在庫数が注文数より少なければ、例外を投げる」
- 意味（方針）: 「在庫が足りない注文は受け付けない」

具体的な変え方:

- **複数行を1行にまとめる**: 日本語1行がコードの範囲に対応し、クリックでその範囲がまとめてハイライトされる。
- **確かめられる主張として書く**: 「〜する」ではなく「〜のはず」。右のコードと上の入出力で確かめる読み方になる。
- **定型的な部分はまとめて畳む**: 入力チェックやログ出力などは1行にして折りたたむ。

チェック方法: 日本語の行数がコードの行数とほぼ同じなら、翻訳になっているサイン。

### 書いてよい範囲（思想4の適用）

| 種類 | 例 | 扱い |
|---|---|---|
| 何をしているか | 在庫が足りない注文は受け付けない | コードから分かるので、そのまま書く |
| なぜそうするか | 分割出荷はしないため | 根拠資料があるときだけ書く |
| 根拠がない理由 | — | 書かない。「要確認」として示す |

### 出典の扱い
- 生成時のルールとしては守る（理由を書けるのは、根拠があるときだけ）。
- 画面には常時表示しない。出典の表示自体が情報の負荷・ノイズになるため。
- 画面上の区別は「断定」と「要確認」の2種類だけ。
- 出典は、気になったときにだけ見られる程度にとどめる。

## 入出力の例の見せ方

- フォーカスした範囲に対応する入出力を出す。
- データ全体ではなく、その範囲で**変わった項目だけ**を「前 → 後」で見せると、情報量をさらに絞れる（案）。

## 既存ツールから取り入れる候補

- 解説とコードの一致を検証する仕組み（balade）。日本語の意味や値のシミュレーションはAIが間違えやすい部分なので、検証できると信頼性が上がる。
