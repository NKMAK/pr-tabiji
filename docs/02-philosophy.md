# 02. 目的・思想・やらないこと

## 目的

AIによってコードが増えても、人間が理解したうえでマージの責任を持てるようにする。

目指すのは、読む時間を削ることではなく、**理解に至るまでの時間を短くする**こと。

## メンタルモデル

**読むことは「仮説を立てて、検証する」ことの繰り返し。**

- 熟練者は「たぶんこういうことだろう」という仮説を先に持ち、コードでそれを確かめながら読む（トップダウン）。
- 仮説がないと、1行ずつ積み上げて意味を推測するしかなく、遅くなる（ボトムアップ）。
- それができる量は、頭の容量（作業記憶）で決まる。

ここから、全体を貫く原則を1つだけ導く。

> **出す情報はすべて「仮説」か「その証拠」のどちらかにする。どちらでもない情報は出さない。**

- 抽象 = 仮説（これから何を理解するのか）
- 具体 = 証拠（実際のコード、データ）

機能の追加や修正で迷ったときは、この原則に照らして判断する。部分最適の積み重ねで全体がちぐはぐになるのを防ぐための基準。

## 思想

### 1. 理解とは、仮説を立てて検証すること
抽象で何を理解するかを先に示し、具体でそれを確かめる。
どの粒度でも「抽象 → 具体」の順を守る。

### 2. 人間の頭の容量は小さい
情報は足すより削る。判断に使わない情報は出さない。
AIの補足情報は、人間にとっては多すぎる。

### 3. 読む軸は1本にする
同じコードを別の切り口で二度読ませない。

### 4. AIは、コードか根拠となる資料から分かることだけを書く
どちらからも分からないことは推測で埋めず、「要確認」として示す。

- コードから分かること: そのまま書く。
- コードからは分からないが、根拠があること: 書いてよい。根拠になるのは、要件・仕様のドキュメント、チケット、PRの説明、テスト、コメント、コミットメッセージなど。
- 根拠がないこと: 推測で書かない。「要確認」として示す。

例:

```
if (stock.available < order.quantity) {
  throw new InsufficientStockError(order.id)
}
```

- 書いてよい: 「在庫が足りない注文はエラーになる」（コードから分かる）
- 根拠がなければ書かない: 「分割出荷はしない仕様のため」（仕様を知らないと分からない）
- 代わりに示す: 「ここは分割出荷をしない仕様か。コードからは判断できない」（要確認）

AIはもっともらしい理由を作ってしまうことがある。間違ったことを断定されるのが一番困る。
「要確認」は、そのまま作者へのレビューコメントとして使える。

### 5. 判断は人間が下す
ツールはレビューやマージの判断を代行しない。人間が理解するのを助けることに徹する。

## 抽象と具体の入れ子

「抽象 → 具体」は、粒度を変えて繰り返される。

| 粒度 | 抽象（仮説） | 具体（証拠） |
|---|---|---|
| PR全体 | 概要（3行程度） | アーキテクチャとデータフローの図 |
| 処理のまとまり | ここで何をするか | その部分のコード |
| 処理単位 | この処理で確かめること | コード、日本語の意味、値を入れた例 |

抽象が先にあるから、具体を読むときに「何を確かめればよいか」が分かっていて、迷わない。

## 既存ツールとの思想の違い

- 既存ツール: AIに説明を**足させる**方向（要約、指摘、問い、チャット）。
- pr-tabiji: 情報を**絞る**ことと、**出す順番**に価値を置く。

差別化は機能の有無ではなく、この思想にある。

## やらないこと

- バグの自動指摘や自動レビュー（すでに多くのツールがある）
- コードの網羅的な説明
- 承認やマージの自動化
- 出す情報量に固定の上限を設けること（「要点は3つまで」など）。量は固定せず、「判断に必要かどうか」で絞る。
