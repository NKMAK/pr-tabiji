# web-verify

**検証を大切にする。** 型チェックやテストが通っただけでは完了にしない。変更した画面・API を実際に動かし、何をして何が見えたかを PR に書く。

プロジェクト固有のこと (起動コマンド、ポート、主要な流れ、テストのコマンド) は CLAUDE.md の「検証」に書く。

## 0. 準備

- 依存が入っているか (`node_modules` など) を確かめる。無ければ lock ファイルに合うコマンド (`npm ci` / `pnpm install --frozen-lockfile`) で入れる。
- 開発サーバーは**バックグラウンドで**起動し (`run_in_background`)、出力からポートを読む。ポートが使用中だと別の番号になる (5173 → 5176 など) ので、決め打ちしない。
- 既に同じプロジェクトのサーバーが動いていれば、それを使ってよい。

## 1. 機械的な確認 (速いものから)

1. 型チェック・lint (`tsc --noEmit`、`eslint` など)
2. ユニットテスト。変えた機能のテストが期待どおりに変わっているか (古い期待値のまま消していないか) も見る。
3. e2e テストがあり、変更が画面に関わるなら、関係する spec だけ流す。

件数と結果を PR の「動作確認」に書く。

## 2. ブラウザで動かす (Claude in Chrome)

- 最初に `tabs_context_mcp`、作業用のタブは `tabs_create_mcp` で新しく作る。終わったら閉じる。
- 連続した操作は `browser_batch` でまとめる。
- **確認の手段の優先順**: ① DOM のテキストと要素の有無 (`read_page` / `find` / `javascript_tool`) ② コンソールのエラー (`read_console_messages`、`onlyErrors: true`。読み始める前のログは取れないので、必要ならリロードしてから読む) ③ スクリーンショットは要所だけ (`scale: 0.5` 程度)。見た目の変更なら最低 1 枚は目で見る。
- 確認すること:
  - 変更した操作の正常系 (クリック、入力、描画など) と、その結果の表示。
  - 変更していない周りの操作が壊れていないか (同じ画面の主なボタンを 1 回ずつ)。
  - コンソールにエラーが出ていないか。
- **スマホ幅**: レイアウトを触ったら `resize_window` で 375×667 程度にして、横スクロール・はみ出し・重なりがないかを見る。終わったら元の大きさに戻す。
- アニメーションのように一瞬で終わるものは、スクリーンショットでは撮れないことが多い。呼ばれたことをテストで確かめ、見た目はユーザーに確認を頼む (PR に「目視は未確認」と書く)。
- `alert` / `confirm` を出す操作は避ける (拡張機能が止まる)。

## 3. 後片付け

- 作ったタブを閉じる。自分で起動したサーバー・一時的なプロセスを止める (ユーザーが見ている最中なら、止めずに URL を伝える)。
- 検証のために書いたデータ (localStorage、テスト用のアカウント・レコード) を消すか、PR に書く。

## 最小の確認 (スモーク、波の区切り)

既定ブランチの先端で、CLAUDE.md に書いた**主要な流れ 1 本**だけを、DOM のテキスト中心で確認する。スクリーンショットは 1〜2 枚まで。

## 落とし穴

- HMR で画面の状態 (お題、カウンター、入力) がリセットされることがある。変更前後の比較は、リロードしてから同じ手順で行う。
- `localStorage` に前回の状態が残っていて、初期表示の確認がずれることがある。初期状態を見るときは消してから。
- 認証やテスト用の値を入れるのは、ローカルの開発サーバー (localhost) に限る。本番の画面では入力しない。
