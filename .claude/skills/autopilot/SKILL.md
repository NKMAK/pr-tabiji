# autopilot

Issue 駆動で、**起票 → 波の判断 → 設計 → 実装 → 検証 → PR → 確認して自動マージ → Issue を閉じる → 進捗更新**を親エージェントが回す。人に聞くのは「8. 止まる条件」だけ。それ以外は既定値で進め、Issue / PR に 1 行で記録する。

プロジェクト固有のこと (検証の手順、競合しやすいファイル、禁止 import、担当者) は CLAUDE.md と `docs/architecture.md` に書く。このファイルには書かない。

## 親のチェックリスト

- **起動前**: ① `.claude/todo/progress.md` を読む ② `git fetch origin` ③ 波を決める (触るファイルと依存が重ならないこと) ④ 依存の追加と共通部品は、親が先に 1 本の PR で入れる ⑤ `progress.md` に波を書く。
- **マージ前 (PR ごと)**: ① 差分が Issue の範囲内か ② 秘密情報がないか ③ ビルド・lint・テストが通ったか ④ **実際に動かした検証の結果が PR にあるか** (CLAUDE.md の「検証」の skill)。1 つでも欠けたらマージしない。
- **波の終わり**: ① 依存元 → 依存先の順でマージ ② **Issue を閉じる** ③ worktree を片付ける ④ `progress.md` を更新 ⑤ 既定ブランチの先端で、マージした機能をまとめて 1 回確認する (スモーク) ⑥ **`retro` skill で振り返り**、繰り返した手順・落とし穴・tips をその場で skill と CLAUDE.md に反映する。
- **区切り (フェーズ完了・大きな機能のまとまり) のとき**: ① `todo.md` を更新 ② 読み取りのみのレビュー (subagent-prompt.md の「レビュー用」) ③ 「高」は直るまで次へ進まない ④ `retro` で、汎用的な改善を my-workflow に戻す ⑤ 次のフェーズを起票する。

## 0. 前提

- 進捗の正は GitHub の Issue と PR。`gh` が使えないときは `.claude/todo/issues.md` を正にする (下の「gh がないとき」)。`progress.md` は、ブロッカーと再開メモの補助。**着手・PR・マージ・中断のたびに親が更新する** (コンテキストが圧縮されても再開できるようにする)。サブエージェントには更新させない。
- ブランチは `origin/<既定ブランチ>` から切り、PR のベースも既定ブランチ。CLAUDE.md にブランチ運用 (dev を挟む等) があればそれに従う。
- **他の人の担当は取らない。** 担当者が付いた Issue と、その範囲のコードには着手しない。
- 外部のエディタやデバイスなど、同時に 1 つしか使えない検証環境 (Unity エディタ、実機) があるときは、並行に実装しても検証は親が順番に行う。

## 1. 起票

```
.claude/skills/autopilot/new-issue.sh "タイトル" 本文ファイル [ラベル]
```

本文に書くこと (Issue だけで着手できるようにする):
- 目的と完了の定義 (何をして、何が見えれば完了か)
- 関連パス: REQ-ID、`docs/impl-plan/`、使う skill
- 触るファイル範囲 (ディレクトリ単位) と、`依存: #N` (なければ「なし」)

Issue 化するのは近いうちに着手する分だけ。先の分は `.claude/todo/todo.md` に書く (立ち上げ期で段階がはっきりしているときだけ、見出しでフェーズに分ける)。

## 2. 波の判断 (親が決める)

1 Issue = 1 サブエージェント = 1 worktree。

- **同じ波**: 触るファイルが重ならず、互いの出力に依存しない。フロントとバックは、API の契約 (パス・型) が固定済みなら並行にできる。
- **波を分ける**: `依存: #N` が未完了、共通部品やマイグレーションを前提にする、同じファイルを変える。
- **競合しやすいファイル** (`package.json` と lock ファイル、ルーティングや DI の登録、共通の型): 依存の追加は親が波の前に 1 本の PR で入れる。登録の行は、どのサブエージェントがどこに足すかをプロンプトで指定する。

## 3. 設計 (Issue の大きさで選ぶ)

- **小さい** (数ファイル): Issue のコメントに 5〜10 行 (変更ファイル、処理の流れ、検証方法) を書いて実装へ。
- **大きい** (複数の REQ にまたがる、新しい機能): `design-flow` skill で `docs/specs/` と `docs/impl-plan/` を作ってから実装する。

## 4. 実装

- 委任するときは、波ごとに 1 メッセージで同時に `Agent` を起動する。`isolation: "worktree"`。プロンプトは [subagent-prompt.md](subagent-prompt.md) を埋めて自己完結させる (サブエージェントはこの会話を知らない)。
- 小さい Issue が 1〜2 本なら、親が直接実装してよい (起動のコストの方が高い)。
- 依存の追加はサブエージェントにさせない。必要になったら報告させ、親が入れる。
- サブエージェントが失敗、または報告が不十分なときは、`SendMessage` で 1 回だけ追加の指示を出す。それでもだめなら、`progress.md` のブロッカーに書いて次へ進む。

## 5. PR と自動マージ (親が行う)

確認 (feat ブランチで実行する):

```
git diff origin/<既定ブランチ> --stat                                       # 範囲外のファイル、.env がないか
git diff origin/<既定ブランチ> | grep -nE '^\+.*(ghp_|github_pat_|sk-|AKIA|password=|token=|API_KEY=.)'   # 秘密情報 (ヒットしたら中身を見る)
```

- ビルド・lint・format の検査・テストが通り (`lint-format` skill)、検証の結果が PR に書かれていること。
- 問題なければマージ: `gh pr merge N --merge` (マージコミットを残す)。順序は依存元 → 依存先。競合したら feat ブランチで既定ブランチを取り込み、検証をやり直してからマージする。
- **マージ後は、親が必ず Issue を閉じる** (`.claude/skills/autopilot/close-issue.sh N "PR #M でマージ"`)。既定ブランチへのマージなら `Closes #N` で閉じるが、波の終わりに `gh issue list --state open` で閉じ忘れを見る。
- そのあと `git worktree remove <パス>` で片付け、`progress.md` を更新する。
- 検証に失敗したらマージしない。直して検証し直す。
- 認証、課金、データの削除、マイグレーションに関わる PR は、マージ前にレビュー用サブエージェントに見せる。

### gh がないとき

`gh` が無く、GitHub API のトークンも使えないときは、GitHub 上の Issue / PR の代わりに次で同じ流れを回す。`gh` が使えるようになったら、未登録の分を GitHub に起票し直す。

1. 起票: `new-issue.sh` が `.claude/todo/issues.md` に `L<番号>` で行を足し、本文を `.claude/todo/issues/L<番号>-<slug>.md` に書く。
2. PR: `feat/*` を push し、PR の本文 (「何を / なぜ / 動作確認」) を本文ファイルの「PR」節に書く。
3. マージ: 確認のあと `git checkout <既定ブランチ>` → `git merge --no-ff feat/xxx -m "Merge feat/xxx: <タイトル> (L<番号>)"` → `git push origin <既定ブランチ>` → feat ブランチを消す。
4. 閉じる: `close-issue.sh L<番号> "<マージコミットのハッシュ>"`。

## 6. スモーク確認 (波の区切り)

既定ブランチの先端で、**主要な流れ 1 本だけ**を確認する (CLAUDE.md の「検証」の skill の「最小の確認」)。結果は `progress.md` か Issue に 1 行で残す。失敗したら新しい Issue を起票して直す。重い確認 (全画面、実機) は、フェーズの最後に 1 回だけ行うか人に頼む。

## 7. 区切りのレビュー

読み取りのみのレビューで次を確認する (直すのは親):
- **秘密情報**: `git ls-files` と `git log -p` に鍵・トークン・`.env` がないか。
- **正しさ**: 明らかなバグ、元に戻す処理・エラー時の処理の漏れ。
- **汎用性・前提**: 特定の環境・名前・値の決め打ちがないか。
- プロジェクト固有の観点は CLAUDE.md に書いたもの (例: 認可、RLS、アップロード可否)。

結果は重大度 (高 / 中 / 低) 別に Issue にする。**高は直るまで次の作業に進まない** (`progress.md` のブロッカーに書く)。

## 8. 止まる条件 (人に聞く)

- **セキュリティ** (鍵・認可・個人情報)、**コスト** (課金が発生する選択)、**技術的に大きな決断** (DB・フレームワークの変更)、**取り消しにくい外部操作** (force push、リポジトリ設定の変更、ブランチの削除、本番データの変更、デプロイを伴うマージ)。
- 操作が権限の確認で拒否されたとき。**言い換えて繰り返さない。** 何をしたかったかと理由を `progress.md` のブロッカーに書き、最後に報告する。
- 要件どうしが矛盾し、どちらを取るかで作りが大きく変わるとき。ユーザーが答えられない時間帯は、推奨案で進めて discussion に「仮決め」と書く。

聞いている間も、関係のない Issue は進める。

## 9. 次の波へ

`git fetch origin` して 2 に戻る。Issue がなくなったら、`docs/specs/` と `.claude/todo/todo.md` から足りない作業を起票して続ける。

## 落とし穴 (実際に起きたこと)

- `git add -A` で worktree (`.claude/worktrees/`) や一時ファイルを誤コミットしかけた。**`git add <パス>` で対象を指定する。**
- worktree で隔離されたエージェントは、`cd ... && git ...` のような複合コマンドを拒否されることがある。git は 1 コマンドずつ実行する。
- macOS の bash は 3.2。スクリプトで `declare -A` などの bash 4 の機能を使わない。
- bash で変数の直後に日本語を続けると (`$VAR、`)、変数名の一部とみなされて unbound variable になる。`${VAR}、` と書く。
- シェルのコマンドに、入力を待つもの (引数なしの `cat` など) を入れない。バックグラウンドに回されて止まる。
- `gh` が無い環境で、git の資格情報からトークンを取り出して API を叩く操作は拒否される。回避しない (「gh がないとき」で進める)。
- `isolation: "remote"` でもローカルの worktree で動くことがある。ネットワークが切れたら、サブエージェントはコミットまでで報告し、親が後で push する。
